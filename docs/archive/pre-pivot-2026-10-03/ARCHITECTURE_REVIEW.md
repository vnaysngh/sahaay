# Sahaay Architecture Review

**Date:** 2026-10-03 (Asia/Kolkata)  
**Status:** Review complete; approved overview/amendments incorporated; unsettled technical recommendations remain explicitly proposed. No product code implemented.

## Conclusion and baseline

The architecture is a suitable foundation for a small launch: TypeScript, one OpenAI Agents SDK agent, native Google tools, PostgreSQL, Temporal, Redis only for ephemeral concerns, deterministic policy, exact approvals and audit. Keep it. The strategic amendment does not justify a redesign, graph database, extra service, custom agent framework or multi-agent architecture.

**Design for the moat. Do not build the moat yet.**

Reviewed all six baseline documents and the strategic amendment/MVP constraint. Source documents explicitly record the latest user correction and revised launch examples. `STRATEGY_REVIEW.md` explains strategy, scope contradictions, seams, and proposed ADR-016–018. The earlier full-capability launch plan is replaced by the current multilingual text/voice launch plan in `IMPLEMENTATION_PLAN.md`.

**NEEDED FOR MVP:** The four general launch actions with Hindi, English and Hinglish text/voice and their minimum identity, account, authorization, approval, durability, history, context and notification controls. Invoice-related capabilities are deferred by accepted user correction ADR-019. Durable reminders/approval waits use Temporal directly; Exactly one accepted meeting/email/reminder composition reuses the existing primitives, without an Autopilot platform.

**DEFER UNTIL VALIDATED:** Moat platforms and unneeded abstractions. Deferring previously included images/documents/Calendar mutations/recurring reminders/semantic retrieval is a clearly documented scope/timing proposal under ADR-017, not silent deletion of the locked PRD or ADR-008. The overview and current user amendments are approved under ADR-019/020; remaining technical decisions retain explicit status.

## Safety mechanics needed for the small launch

### NEEDED FOR MVP — action evidence and uncertain outcomes

A unique local key alone cannot prevent the provider-accepted/database-not-recorded gap. Atomically persist/claim an immutable action scoped to user/account/workflow/logical ID, payload version/hash and attempts. Track prepared, executing, succeeded, failed and outcome-unknown states. Recover an abandoned executing action as uncertain until evidence establishes its result. Approval consumption authorizes that logical action, not arbitrary new IDs on retry.

The [Gmail send contract](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send) exposes no general idempotency-key parameter. This review infers that the baseline local-key recipe is insufficient for guaranteed deduplication. A generated MIME Message-ID is correlation evidence, not a documented provider deduplication guarantee. Persist provider message/thread IDs; investigate bounded sent-message reconciliation. If evidence is inconclusive, block and show an actionable uncertain result. A negative search result is not enough to blindly resend. The same principle applies to WhatsApp notifications. API acceptance is not proof of recipient delivery.

### NEEDED FOR MVP — authority, execution and cancellation

PostgreSQL owns product facts, immutable proposals, permissions/approvals and action evidence. Temporal owns deterministic orchestration and timer/execution history. A small outbox atomically committed with product decisions delivers stable workflow starts/signals; the existing worker retries dispatch, with duplicate-safe consumers. DB status is a versioned projection, not a competing scheduler.

SDK/module calls produce domain proposals; the model cannot manipulate credentials or authorize itself. Read tools check current permission without requiring human approval. Side effects check current permission, exact approval, expiry, account connection, disable controls and cancellation immediately before dispatch. No approved text is regenerated during replay. [Temporal determinism documentation](https://docs.temporal.io/workflow-definition) supports isolating I/O in Activities. [Official OpenAI guardrail guidance](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) explains why agent-level guardrails alone do not protect every sensitive tool boundary.

Cancel before dispatch stops pending work; cancel racing an accepted/in-flight send cannot unsend it. Report actual evidence. Clarify ambiguous “cancel that” and recipient/date targets. Credentials never enter model inputs, frontend responses, logs or Temporal arguments/results.

### NEEDED FOR MVP — provider gates, not new platforms

Google classifies Gmail read/compose scopes as restricted and send as sensitive; request only launch operations. Review [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) and [restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification) for test versus public readiness, server-side data handling and exceptions. Dedicated test success is not public verification.

The [WhatsApp messaging policy](https://whatsappbusiness.com/policy/) requires opt-in and approved templates outside the 24-hour customer-service window. Delayed reminder notices need a permitted out-of-window route. Keep sensitive email bodies in the authenticated approval inbox where needed. The [official terms entry point](https://www.whatsapp.com/legal/business-solution-terms) was login-restricted during the initial review; personal-AI-assistant eligibility remains unverified. Record provider confirmation/applicable accessible terms before live launch; do not invent eligibility. These sources were checked during the initial 2026-10-03 review and must be revalidated at implementation/provider setup if changed.

### DEFER UNTIL VALIDATED — broader mutation adapters and moat machinery

Calendar mutation deduplication/concurrency controls are necessary when those writes are added, but not part of a read-only launch. Relevant future references are [Calendar creation IDs](https://developers.google.com/workspace/calendar/api/guides/create-events) and [ETag conditional modifications](https://developers.google.com/workspace/calendar/api/guides/version-resources). Do not implement those adapters now merely to demonstrate optionality.

Use a direct OpenAI module seam, simple SQL context, existing action-event history and named Temporal workflows. No graph/Autopilot/behavioral/provider-routing platform is required. Future India integrations remain outside the scope and are not pre-modeled.

## MVP acceptance evidence

**NEEDED FOR MVP:** Launch actions complete with ambiguity, deny/reject/expiry/edit, restart/replay, provider failure, uncertain send, duplicate input/action/webhook, cross-user access, prompt injection, credential redaction and cancellation cases. Current-state revocation and accepted-but-unrecorded crashes must prevent unauthorized/duplicate sends. Scheduling dispatch recovery and delayed notifications must be demonstrably safe. User can see what happened, stop pending work and correct/remove explicit personal context. Test the sole composed meeting/email/reminder workflow across languages/text/voice, including ambiguity/partial failures, one reminder and restart-safe delivery. Prove informational reads work when Temporal is stopped. Calendar creation remains outside acceptance.

**DEFER UNTIL VALIDATED:** Sophisticated memory/graph/behavior benchmarks, generic Autopilot scenarios, multiple models and unimplemented integration fault suites. Failure/security tests for those capabilities become mandatory before they are enabled, not before this scoped launch. No extra cross-service workflow or infrastructure is added.

The revised review is complete. No product implementation or provider actions were performed. Scope/ADR dispositions remain explicit documentary gates rather than silent architectural changes.
